信创项目要求同时兼容桌面端（UOS/银河麒麟）和移动端。底层是 Debian/Ubuntu 体系，但开发时在架构选型、环境依赖、UI 规范上踩了不少坑。以下按桌面端、移动端、后端三层整理实际落地经验。

## 桌面端：UOS 与银河麒麟

主流是 UOS（Deepin）和银河麒麟，社区里也常有欧拉 Euler。

### GUI 方案选型

- **Web 跨端：Vue 3 + Electron**。在 ARM/龙芯架构下，Electron 的某些原生模块需要手动重新编译。老旧信创系统的浏览器内核版本极低，如果 Vue 项目用了过多现代语法（如 Optional Chaining），必须配好 babel 插件，否则白屏。
- **Avalonia（.NET）**：依托 dotnet 兼容性好，可交叉编译——Windows 直接打包 arm64 可用包。但界面效果不如直接写前端。Electron 只能在各自架构上打包，吃内核版本。
- **原生 C++/Qt**：理论性能最优，但受 glibc、stdc++ 版本和依赖库混乱所累，别说适配，各编一份都是大工程。

实操中平台适配性最好的是 Electron、.NET、Java，可惜这些在性能相对孱弱的信创芯片上劣势被放大，主界面好几秒才出。

### 权限与路径

国产系统对 `/root` 及部分系统目录权限控制极严。所有配置文件和缓存一律写入 `$HOME/.config/` 下，避免运行报错。

### UOS 的"仿 Windows"陷阱

UOS 仿 Windows 设计，存储被弄成 C 盘 D 盘，导航混乱。此外政府/敏感部门常不能联网，三个系统库多被阉割，你可能需要把依赖额外封装一份进安装包——本来就不小的安装包更重了。

UOS 路线保守，底层用较旧的 debian10，保有量极大。为现代 Linux 编译的软件几乎难运行到 UOS 上。26 年起连一些因为原生库用了 c++20 的 Electron 程序（落雪音乐助手、VSCode 官方版、Trae 官方版等）也开始无法在 UOS 运行。

### 架构排列组合

要面对的芯片架构（x86_64、arm64（华为用 gles 导致大量不兼容常规 arm）、mips、loongarch64、long64、sw64）×系统版本（UOS、deepin v20/v23/v25 之间常互相不兼容，不只向后也向前；银河麒麟/优麒麟；红旗；欧拉；鸿蒙）的交叉合集，适配种类是两侧的排列组合，维护者头皮发麻。

## 移动端：跨端与类型约束

跨端复用采用 uni-app 或 Taro，配合 TS 强制类型约束。信创业务逻辑变动频繁，强类型能减少很多低级错误。

## 后端：.NET 与 Python 的国产化表现

### 运行时

- **.NET 6/8** 在国产系统上表现稳定。但用 `System.Drawing` 等涉及 GDI+ 的库时，必须在镜像里安装 `libgdiplus`，否则验证码、图片处理直接挂掉。
- **Python**：注意 C 扩展模块兼容性，建议在目标架构（如 ARM64）的开发机上直接构建 `whl` 包。

### 数据库兼容

与达梦、人大金仓对接时，若用 EF Core，提前确认官方驱动兼容版本。部分国产数据库对 `DateTime` 的处理与 SQL Server/MySQL 略有出入。

## 实战心得

- **架构测试**：别在 x86 上写完代码就完事。买飞腾或鲲鹏小主机做 CI/CD，很多逻辑错误只在 CPU 架构变化时暴露。
- **UI 规范**：信创项目对 UI 常有特定要求（字体大小、配色对比度）。早点拿到规范手册，省得后期改 CSS 改到头大。
- **deepin 大版本升级**：有案例在 deepin 20.9 能启动的软件，升级到 23 之后再也打不开。

信创适配的核心不是单点技术突破，而是"芯片 × 系统 × 库版本"的矩阵化测试纪律。
